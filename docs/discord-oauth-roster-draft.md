# OWKR 내전표 · Discord OAuth 도입 초안

## 1. 목적

OWKR Match에 다음 기능을 도입한다.

1. 구글 시트 형식으로 운영진용 유저 정보 목록을 저장하고 조회한다.
2. Discord OAuth로 운영자 신원을 확인한다.
3. `ADMIN_USER_IDS`에 등록된 Discord 계정만 내전표를 열람·수정한다.
4. 민감한 운영 메모는 공개 시트, 브라우저 저장소, 결과 이미지에 노출하지 않는다.
5. 참가자 동명이인은 배틀태그로 구분하고, OAuth의 Discord 사용자 ID는 로그인한 운영자 권한 확인에만 사용한다.

## 2. 핵심 결정

### 2.1 참가자 식별

| 값 | 용도 | 고유성 |
|---|---|---|
| Discord 표시 이름 | 참여 대조와 화면 표시 | 중복 가능 |
| 배틀태그 | 게임 참가자 식별 | 명단 내 고유값으로 취급 |

- 채팅으로 입력되는 현재 참가자와 운영진용 유저 시트는 서로 다른 데이터로 관리한다.
- 참가자의 실질적인 고유 키는 배틀태그로 사용한다.
- 유저 시트와 현재 참가자는 배틀태그가 일치할 때만 화면에서 연결한다.
- 일반 Discord 채팅 복붙에는 메시지 작성자의 숫자 사용자 ID가 포함되지 않으므로 참가자 ID로 사용할 수 없다.
- 같은 Discord 표시 이름이 여러 명이면 자동 완료하지 않고 배틀태그 후보를 보여준다.

OAuth에서 받는 숫자 Discord 사용자 ID는 앱에 직접 로그인한 운영자 본인을 식별하는 용도다. 채팅을 작성한 참가자의 ID와 연결되지 않으며 참가자 대조에도 사용하지 않는다.

### 2.2 메모 분리

특이사항을 공개 정보와 비공개 정보로 분리한다.

| 구분 | 예시 | 저장 위치 | 노출 범위 |
|---|---|---|---|
| 운영 상태 | 마이크 미사용, 지각 예정, 중도 퇴장 예정 | 내전표 또는 참가자 데이터 | 허용된 운영자 |
| 공동 운영 메모 | 반복 노쇼, 운영상 주의점 | 서버 데이터베이스 | 관리자·운영진 |
| 나만 보는 메모 | 개인적으로 확인할 내용 | 서버 데이터베이스 | 작성자 본인 |

- 비공개 운영 메모는 구글 시트 복붙 형식에 포함하지 않는다.
- 비공개 운영 메모는 `localStorage`에 저장하지 않는다.
- 비공개 운영 메모는 팀 결과 이미지, 클립보드 복사, 브라우저 콘솔, 오류 로그에 포함하지 않는다.
- 참가자 본인에게 노출할 수 없는 내용은 `privateNote`로만 저장한다.
- 메모 작성 시 `관리자 공유`와 `나만 보기`를 선택하고, 기본값은 `나만 보기`로 둔다.

## 3. 시트 초안

### 3.1 권장 열

| Discord 표시 이름 | 배틀태그 | 탱커 | 딜러 | 힐러 | 특이사항 |
|---|---|---|---|---|---|
| 상만 | PlayerOne#1234 | 다3! | 플2? | 골1 | 마이크X |
| 롤랑 | Roland#5678 | 플1 | 다4! | 플2 | |

### 3.2 기록 규칙

- 탱커·딜러·힐러 값은 운영진이 참고하는 유저 정보로 보존한다.
- 특이사항은 유저별 참고 정보이며 개인·공유 운영 메모와 분리한다.
- 시트의 티어와 특이사항은 현재 참가자 명단이나 팀 배정 알고리즘에 자동 반영하지 않는다.

### 3.3 유저 시트 흐름

1. 상단 `유저 시트`에서 저장된 전체 유저 목록을 조회한다.
2. 유저를 선택하면 배틀태그·역할별 티어·특이사항을 읽기 전용으로 확인한다.
3. `전체 시트 편집`에서 시트의 6개 열을 붙여넣거나 직접 수정한다.
4. 중복되거나 잘못된 배틀태그를 수정한 뒤 전체 시트를 저장한다.
5. 현재 참가자의 배틀태그가 시트에 있으면 참가자 카드에 바로가기 아이콘을 표시한다.
6. Discord 명단 형식으로 가져오면 배틀태그 기준 신규 행을 추가하고 기존 행의 이름·티어를 갱신한다.
7. Discord 명단으로 기존 행을 갱신할 때 특이사항은 보존한다.

실시간 Google Sheets API 연동은 1차 범위에서 제외한다. 정적 프런트엔드, Google 권한, Discord 권한을 한 번에 결합하지 않고 복사·붙여넣기부터 안정화한다.

## 4. 인증과 권한

### 4.1 OAuth 범위

1차 범위:

- `identify`: 로그인 사용자의 Discord 사용자 ID, 사용자명, 표시 이름, 아바타 확인

이메일, 친구, DM, 메시지 읽기 권한은 요청하지 않는다.

### 4.2 로그인 흐름

1. 사용자가 `Discord로 로그인`을 누른다.
2. 서버가 일회용 `state`를 생성해 세션에 저장한다.
3. Discord 승인 화면으로 이동한다.
4. Discord가 서버의 콜백 주소로 `code`와 `state`를 전달한다.
5. 서버가 `state`를 검증한다.
6. 서버가 `client_secret`을 사용해 코드를 액세스 토큰으로 교환한다.
7. 서버가 현재 사용자 정보를 조회한다.
8. Discord 사용자 ID가 `ADMIN_USER_IDS`에 포함되는지 확인한다.
9. 서버가 자체 세션을 만들고 `HttpOnly`, `Secure`, `SameSite=Lax` 쿠키를 발급한다.
10. Discord 액세스 토큰은 필요한 조회가 끝나면 폐기한다.

Discord `client_secret`, 세션 서명 키, 데이터베이스 비밀번호는 프런트엔드 번들에 포함하지 않는다.

### 4.3 관리자 허용 목록

- `ADMIN_USER_IDS`에는 접근을 허용할 Discord 사용자 숫자 ID를 쉼표로 구분해 저장한다.
- Discord 로그인 성공과 앱 접근 허용은 별개로 처리한다.
- 모든 비공개 API는 요청마다 서버 세션을 검사한다.
- 프런트엔드에서 버튼만 숨기는 방식으로 권한을 대신하지 않는다.
- 허용 목록에서 제거된 사용자는 다음 로그인 또는 짧은 세션 만료 후 접근이 해제된다.

## 5. 권장 배포 구조

현재 GitHub Pages는 정적 파일만 배포하므로 OAuth 코드 교환, 세션 발급, 비공개 메모 저장을 안전하게 처리할 서버가 없다.

### 권장안

프런트엔드와 API를 같은 출처로 배포한다.

```text
브라우저
  ├─ React 화면
  └─ Secure HttpOnly 세션 쿠키
          │
          ▼
OWKR 웹 서버
  ├─ Discord OAuth 콜백
  ├─ 세션·권한 검사
  ├─ 유저 시트 API
  ├─ 비공개 메모 API
  └─ 감사 로그
          │
          ▼
Upstash Redis (1차) / PostgreSQL (내전표 서버 저장 확장 시)
```

- 1차 구현: Vercel 정적 프런트엔드 + Functions + Upstash Redis
- 확장안: 내전표 공동 저장·감사 로그 도입 시 PostgreSQL 추가
- 대안: Cloudflare Pages + Workers + D1/PostgreSQL
- GitHub Actions는 검사 용도로 유지할 수 있다.
- GitHub Pages 배포는 새 서비스 전환 후 중단하거나 공개 데모 전용으로 분리한다.

같은 출처를 권장하는 이유는 세션 쿠키, CORS, OAuth 콜백, CSRF 방어 구성을 단순하게 유지하기 위해서다.

## 6. 데이터 모델 초안

### `users`

| 필드 | 설명 |
|---|---|
| `id` | 내부 사용자 ID |
| `discord_user_id` | OAuth로 받은 Discord 사용자 ID, 고유 |
| `username` | Discord 사용자명 |
| `global_name` | Discord 표시 이름 |
| `avatar` | 아바타 식별자 |
| `last_login_at` | 마지막 로그인 |

### `matches`

| 필드 | 설명 |
|---|---|
| `id` | 내전 ID |
| `title` | 내전명 |
| `scheduled_at` | 진행 일시 |
| `status` | 준비, 확정, 종료 |
| `created_by` | 생성 운영자 |
| `created_at`, `updated_at` | 변경 시각 |

### `match_participants`

| 필드 | 설명 |
|---|---|
| `id` | 참가 행 ID |
| `match_id` | 내전 ID |
| `discord_name` | 참가자의 Discord 표시 이름 |
| `battle_tag` | 배틀태그 |
| `tank_rank`, `dps_rank`, `support_rank` | 역할별 티어 원본값 |
| `no_mic` | 마이크 미사용 |
| `match_note` | 해당 내전에서만 쓰는 운영 상태 |
| `sort_order` | 참가자·대기열 순서 |

### `player_private_notes`

| 필드 | 설명 |
|---|---|
| `id` | 메모 ID |
| `battle_tag_normalized` | 참가자 연결 키 |
| `note` | 비공개 운영 메모 |
| `visibility` | `OWNER_ONLY` 또는 `ADMINS` |
| `created_by`, `updated_by` | 작성·수정 운영자 |
| `created_at`, `updated_at` | 작성·수정 시각 |

### `audit_logs`

| 필드 | 설명 |
|---|---|
| `actor_user_id` | 작업한 운영자 |
| `action` | 생성, 수정, 삭제, 내보내기 |
| `target_type`, `target_id` | 대상 |
| `created_at` | 작업 시각 |

감사 로그에는 비공개 메모 본문을 저장하지 않고 “누가 어느 참가자의 메모를 수정했다”는 사실만 남긴다.

## 7. API 초안

### 인증

- `GET /api/auth/login`
- `GET /api/auth/callback`
- `POST /api/auth/logout`
- `GET /api/auth/me`

### 내전표

- `GET /api/matches`
- `POST /api/matches`
- `GET /api/matches/:matchId`
- `PUT /api/matches/:matchId`
- `POST /api/matches/:matchId/import`
- `DELETE /api/matches/:matchId/participants/:participantId`

### 비공개 메모

- `GET /api/notes?battleTag=:battleTag`
- `PUT /api/notes`

비공개 메모 API는 `ADMIN_USER_IDS`에 등록된 로그인 사용자만 사용할 수 있다. `OWNER_ONLY` 메모는 작성자 본인에게만 반환하고, `ADMINS` 메모만 등록된 관리자 사이에서 공유한다.

## 8. 화면 초안

### 비로그인

- 서비스 소개
- `Discord로 로그인`
- 공개 팀 결과가 필요한 경우에만 별도 공유 링크 제공

### 로그인 후

- 상단: Discord 이름, 로그아웃
- 내전 목록: 예정·종료 내전
- 내전 상세:
  - 시트 붙여넣기
  - 참가자·대기열 관리
  - 참여 대조
  - 팀 자동 배정
  - 운영 상태
  - 권한이 있을 때만 비공개 메모

### 비공개 메모

- 기본 상태에서는 접혀 있어야 한다.
- 열람 권한이 없는 사용자에게는 필드 자체를 응답하지 않는다.
- 작성 화면에서 `나만 보기`와 `관리자 공유`를 명확히 구분한다.
- 팀 결과 이미지와 복사 기능에서 제외한다.
- 수정 시 작성자와 수정 시각을 표시한다.

## 9. 보안 기준

- OAuth `state` 검증 필수
- Discord `client_secret` 서버 전용
- 세션 쿠키는 `HttpOnly`, `Secure`, `SameSite=Lax`
- 로그인 직후와 권한 변경 시 세션 ID 재발급
- 변경 API는 CSRF 방어 적용
- 모든 SQL은 파라미터 바인딩 사용
- 비공개 메모를 URL, 분석 이벤트, 오류 메시지에 포함하지 않음
- 내전표 조회·수정·메모 열람을 감사 로그로 기록
- 운영자 세션은 짧게 유지하고 재로그인으로 Discord 역할을 다시 확인
- 데이터 백업과 운영자 탈퇴 시 접근 회수 절차 마련

## 10. 구현 단계

### 1단계: 유저 시트

- 유저 목록과 읽기 전용 상세 조회
- 별도 `전체 시트 편집` 진입
- 넓은 Google Sheets형 유저 편집 화면
- TSV 파서
- 다중 셀 붙여넣기와 직접 셀 수정
- 행별 배틀태그 오류·중복 표시
- 유저별 티어·특이사항 저장
- 현재 참가자와 배틀태그 기반 유저 정보 연결

### 2단계: Discord 로그인 기반

- 새 배포 환경 구성
- Discord 애플리케이션 생성
- OAuth 시작·콜백·로그아웃
- 서버 세션
- `identify` 기반 사용자 저장

### 3단계: 관리자 허용 목록

- `ADMIN_USER_IDS` 등록 여부 검사
- 모든 비공개 API의 서버 세션 검사
- 접근 거부 화면

### 4단계: 내전표 서버 저장

- 내전·참가자 데이터베이스
- 운영자 간 공동 열람·수정
- 충돌 방지를 위한 `updated_at` 또는 버전 검사
- 감사 로그

### 5단계: 비공개 메모

- 배틀태그 기준 비공개 메모
- 권한별 열람·수정
- 결과 이미지·복사·로그 제외 검증
- 보존 기간과 삭제 정책 확정

## 11. 1차 완료 조건

- `ADMIN_USER_IDS`에 없는 Discord 사용자는 내전표에 접근할 수 없다.
- 유저 시트는 현재 참가자 명단과 분리해 조회·수정할 수 있다.
- 현재 참가자와 같은 배틀태그의 유저 정보를 연결해 볼 수 있다.
- 같은 Discord 표시 이름은 배틀태그로 구분된다.
- 비공개 메모는 서버에만 저장되고 권한 없는 응답에 포함되지 않는다.
- 비공개 메모는 이미지·클립보드·브라우저 저장소·감사 로그 본문에 노출되지 않는다.
- 운영자 추가·삭제·메모 변경 이력을 확인할 수 있다.

## 12. 구현 전 확정할 항목

1. 접근을 허용할 Discord 사용자 ID 목록
2. `OWNER_ONLY` 메모를 작성자 외 관리자가 열람할 수 있는지 여부
3. 메모 보존 기간과 삭제 정책
4. 새 배포 환경 선택
5. 공개 결과 공유 링크를 로그인 없이 허용할지 여부
